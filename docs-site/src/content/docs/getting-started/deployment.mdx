# Deployment

This guide covers all deployment options for Beacon: the Home Assistant add-on, standalone Docker, reverse proxy setup, hardware recommendations, kiosk mode configuration, and performance optimization.

---

## HA Add-on deployment

The simplest deployment. See [Getting Started](/docs/getting-started/installation/) for the step-by-step installation.

**How it works under the hood:**

Home Assistant pulls `ghcr.io/asachs01/beacon` for the version in `beacon/config.yaml`. It does not build the add-on on the device. CI builds that image from `beacon/Dockerfile` before the version is published.

1. The Dockerfile uses a two-stage build:
   - **Build stage**: Node.js 20 Alpine builds the Vite/React app (`npm ci && npm run build`)
   - **Runtime stage**: Based on `ghcr.io/hassio-addons/base:16.3.2`, installs Node.js and the `serve` static file server
2. `run.sh` runs at container start:
   - Reads add-on options from `/data/options.json` via `bashio::config`
   - Generates `runtime-config.js` with the configuration values
   - Injects the script tag into `index.html`
   - Starts `serve` on port 3000
3. HA's ingress proxy forwards requests from the sidebar panel to port 3000

**Health check**: The container includes a health check that runs every 30 seconds:
```
wget -qO /dev/null http://localhost:3000/ || exit 1
```

## Docker standalone deployment

For running Beacon outside of Home Assistant's add-on system (Docker, Docker Compose, or Kubernetes). The container talks to Home Assistant, so `HA_URL` must be reachable from the container. On your trusted home network, the browser only needs to reach Beacon; it does not talk to Home Assistant directly.

:::caution
Anyone who can reach Beacon's port can use its Home Assistant access. Keep that port on your trusted home network (your LAN) and never forward it to the internet or expose it beyond your LAN. In the add-on, use the Home Assistant sidebar panel (ingress) where you can; it sits behind your Home Assistant login. If you need remote access, use the add-on's ingress panel, Home Assistant's own remote access, a VPN, or a reverse proxy that requires authentication.
:::

This needs Beacon **1.50.1** or later. **Changed in 1.50.1.**

Create a long-lived access token in Home Assistant first. Open your profile (your name at the bottom of the sidebar), scroll to **Long-Lived Access Tokens**, choose **Create Token**, name it Beacon, and copy the value. Home Assistant shows the token only once. Pass that value as `HA_TOKEN`. Do not set `SUPERVISOR_TOKEN` on a standalone container. That variable is injected by the Supervisor and selects add-on mode.

The [Home sensors](/docs/features/home-sensors/) card (Beacon **1.53.0** or later) uses this token through the server's `/beacon-ws/ha` proxy. It can read only the entities that the Home Assistant user for that long-lived token can read.

### Basic deployment

```bash
docker run -d \
  --name beacon \
  --restart unless-stopped \
  -p 3000:3000 \
  -v beacon-data:/data \
  -e HA_URL="http://192.168.1.100:8123" \
  -e HA_TOKEN="YOUR_LONG_LIVED_TOKEN" \
  -e FAMILY_NAME="Sachs" \
  -e THEME="midnight" \
  -e WEATHER_ENTITY="weather.home" \
  ghcr.io/asachs01/beacon:latest
```

To keep the token out of your shell history, put `HA_URL` and `HA_TOKEN` in a `.env` file (do not commit it) and replace the two `-e HA_URL` / `-e HA_TOKEN` lines with `--env-file .env`.

`HA_URL` is the Home Assistant base URL, with no path on the end — for example `http://homeassistant.local:8123` or `http://192.168.1.100:8123`, with no `/api`. `http://` and `https://` both work. A trailing slash is stripped. Beacon builds the REST URL from that value, and builds the websocket URL by changing `http` to `ws` or `https` to `wss` and appending `/api/websocket`. The `beacon-data` volume keeps family members, chores, settings, and meal plans when the container is recreated.

### Docker Compose

```yaml
version: "3.8"
services:
  beacon:
    image: ghcr.io/asachs01/beacon:latest
    container_name: beacon
    restart: unless-stopped
    ports:
      - "3000:3000"
    volumes:
      - beacon-data:/data
    environment:
      HA_URL: "http://192.168.1.100:8123"
      HA_TOKEN: "${HA_TOKEN}"
      FAMILY_NAME: "Sachs"
      THEME: "midnight"
      AUTO_DARK_MODE: "true"
      WEATHER_ENTITY: "weather.home"
      PHOTO_DIRECTORY: "/media/beacon/photos"
      PHOTO_INTERVAL: "30"
      SCREEN_SAVER_TIMEOUT: "5"

volumes:
  beacon-data:
```

Put the long-lived access token in a `.env` file next to the Compose file as `HA_TOKEN=...`, or replace `${HA_TOKEN}` with the token. Do not commit the token.

### Building from source

```bash
git clone https://github.com/asachs01/beacon.git
cd beacon
docker build -t beacon .
docker run -d --name beacon -p 3000:3000 \
  -v beacon-data:/data \
  --env-file .env \
  beacon
```

### Advanced: URL overrides

`HA_API_BASE_OVERRIDE` and `HA_WS_URL_OVERRIDE` still work, and they take precedence over the URLs Beacon would build from `HA_URL`. Set them if you need the REST or websocket address to be something other than that built URL. The override values are used as given, including a trailing slash.

```bash
HA_API_BASE_OVERRIDE=http://192.168.1.100:8123
HA_WS_URL_OVERRIDE=ws://192.168.1.100:8123/api/websocket
```

Use `wss://` when Home Assistant is served over HTTPS. On a standalone container, authentication still uses `HA_TOKEN`. Do not set `SUPERVISOR_TOKEN`.

## Reverse proxy setup

If you put Beacon behind a reverse proxy. A reverse proxy that is reachable from outside your LAN must require authentication. Do not forward Beacon's port on its own.

:::caution
Anyone who can reach Beacon's port can use its Home Assistant access. Keep that port on your trusted home network (your LAN) and never forward it to the internet or expose it beyond your LAN. In the add-on, use the Home Assistant sidebar panel (ingress) where you can; it sits behind your Home Assistant login. If you need remote access, use the add-on's ingress panel, Home Assistant's own remote access, a VPN, or a reverse proxy that requires authentication.
:::


### Nginx

```nginx
server {
    listen 443 ssl;
    server_name beacon.yourdomain.com;

    ssl_certificate /path/to/cert.pem;
    ssl_certificate_key /path/to/key.pem;

    location / {
        proxy_pass http://127.0.0.1:3000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # WebSocket support (for HA API passthrough)
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
    }
}
```

### Caddy

```
beacon.yourdomain.com {
    reverse_proxy localhost:3000
}
```

Caddy handles SSL certificates automatically via Let's Encrypt.

### Important notes

- The standalone container calls Home Assistant itself. The browser talks to Beacon, and Beacon calls `HA_URL` with `HA_TOKEN`. The reverse proxy in front of Beacon does not need to reach Home Assistant.
- A development server (`npm run dev`) is different: the browser talks to Home Assistant directly, so that browser must be able to reach `VITE_HA_URL`.
- Keep Beacon and Home Assistant on the same trusted network. If the reverse proxy is reachable from outside your LAN, it must require authentication.

## Kiosk mode setup

Kiosk mode locks the device to showing only Beacon, preventing accidental navigation or app switching.

Beacon's own **Kiosk Mode** (Settings > Display) hides the sidebar. It stays hidden until a parent long-presses the top corner for about 2 seconds or taps it 3 times quickly (hold Escape on a keyboard). Navigation hides again after about 15 seconds of inactivity, and a family PIN is required when one is set. Turn **Reveal navigation gesture** off to remove that way back. Kid Display uses the same gesture to exit: a PIN when one is set, otherwise a confirm. See [the FAQ](/docs/reference/faq/#how-do-i-hide-the-sidebar-for-wall-tablets--kiosk-setups).

### Android (Fully Kiosk Browser)

[Fully Kiosk Browser](https://www.fully-kiosk.com/) is the recommended kiosk solution for Android tablets.

1. Install Fully Kiosk Browser from the APK (it is not on the Play Store)
2. Set the **Start URL** to your Beacon address
3. Enable these settings:
   - **Web Auto Reload**: Enable, set to reload on connectivity change
   - **Keep Screen On**: Yes
   - **Screen Brightness**: 40-60%
   - **Autostart on Boot**: Yes
   - **Kiosk Mode**: Enable (requires device admin)
   - **Hide Status Bar**: Yes
   - **Hide Navigation Bar**: Yes
   - **Disable Home Button**: Yes (kiosk mode)

### Chrome kiosk mode (desktop/Raspberry Pi)

```bash
chromium-browser \
  --kiosk \
  --noerrdialogs \
  --disable-translate \
  --disable-infobars \
  --disable-session-crashed-bubble \
  --disable-features=TranslateUI \
  --autoplay-policy=no-user-gesture-required \
  http://YOUR_BEACON_URL
```

Add this to a startup script (`~/.config/autostart/beacon.desktop` on Linux):

```ini
[Desktop Entry]
Type=Application
Name=Beacon
Exec=chromium-browser --kiosk --noerrdialogs http://YOUR_BEACON_URL
```

### Firefox kiosk mode

```bash
firefox --kiosk http://YOUR_BEACON_URL
```

### iPad Guided Access

1. Open Beacon in Safari
2. Triple-click the side button to enable Guided Access
3. Tap **Start** — the iPad is now locked to Safari
4. To exit, triple-click the side button and enter your passcode

## Multi-display setup

You can run Beacon on multiple displays simultaneously. Each display:

- Connects to the same Home Assistant instance
- Shows the same calendar events (since they come from HA)
- Has its own independent localStorage (family members, chores, theme preference)
- Can be configured with different themes or family names

### Example: Kitchen + Living Room

1. Set up a Fire tablet in the kitchen with the Skylight theme
2. Set up a Raspberry Pi + monitor in the living room with the Midnight theme
3. Both connect to the same HA URL and show the same calendars

## Performance optimization

### For tablets

- **Disable animations**: If the tablet is low-powered, some browsers allow disabling CSS animations via `prefers-reduced-motion`
- **Reduce photo resolution**: Resize photos to 1920x1080 before adding them to the photo directory
- **Increase refresh intervals**: In development, you can modify the refresh intervals (events: 5 min, weather: 10 min, grocery: 2 min) to reduce API calls

### For Raspberry Pi

- **Use Chromium**: It performs better than Firefox on ARM
- **Disable GPU compositing** if you see rendering artifacts: `--disable-gpu`
- **Allocate more GPU memory**: In `config.txt`, set `gpu_mem=128` or higher
- **Use a lightweight window manager**: `openbox` is sufficient — no need for a full desktop environment

### General

- Beacon's production build is a static site served by `serve`. It has minimal server overhead.
- The main resource consumption is in the browser (JavaScript, DOM rendering, WebSocket connection).
- Network usage is minimal: WebSocket messages for state changes, REST API calls for photos and grocery data.
- The health check (`wget` every 30 seconds) has negligible impact.

## Troubleshooting

### Container does not start

1. Check Docker logs: `docker logs beacon`
2. Confirm the log says `Mode: standalone` and `Home Assistant token: available`. The log never prints the token.
3. `HA_TOKEN` must be a current long-lived access token (Profile → Long-Lived Access Tokens). `HA_URL` must be reachable from the container (try `docker exec beacon wget -qO- "$HA_URL/api/"`).

Missing `HA_URL` or `HA_TOKEN` does not stop the container. See the next section.

### `HA_URL` or `HA_TOKEN` is missing

The UI still loads, but it has no Home Assistant data. Beacon logs this exact error:

```
Standalone mode needs HA_URL and HA_TOKEN. Set HA_URL to your Home Assistant base URL and HA_TOKEN to a long-lived access token from Profile → Long-Lived Access Tokens. Beacon will keep serving the UI.
```

Set both variables and recreate the container. `HA_URL` must be the base URL (no `/api` path).

### `getaddrinfo ENOTFOUND supervisor`

The container is trying to reach Home Assistant at the add-on Supervisor hostname (`supervisor`) and cannot resolve it. That was the bug in [#119](https://github.com/asachs01/beacon/issues/119), fixed in **1.50.1**. On 1.50.1 or later, set `HA_URL` and `HA_TOKEN` as in the standalone section above, and do not set `SUPERVISOR_TOKEN`.

On images older than 1.50.1, set these two overrides as a workaround, and put the long-lived access token in `SUPERVISOR_TOKEN` (those images authenticate with that variable, not `HA_TOKEN`):

```bash
-e SUPERVISOR_TOKEN="YOUR_LONG_LIVED_TOKEN" \
-e HA_API_BASE_OVERRIDE="http://YOUR_HA_IP:8123" \
-e HA_WS_URL_OVERRIDE="ws://YOUR_HA_IP:8123/api/websocket"
```

Use `wss://` when Home Assistant is served over HTTPS. This workaround was not the supported standalone setup; upgrade to 1.50.1 or later when you can.

### Beacon loads but shows "Demo Mode"

This means Beacon could not connect to Home Assistant. The UI can still load. Check:
1. `HA_URL` is set as a base URL (no `/api` path) and is reachable from the container. On your trusted home network, the browser only needs to reach Beacon.
2. `HA_TOKEN` is a valid long-lived access token
3. You did not set `SUPERVISOR_TOKEN` on a standalone container
4. The Home Assistant instance is running and the API is accessible

### Display goes to sleep / screen turns off

This is controlled by the device's OS, not by Beacon. Disable screen timeout:
- **Android**: Settings > Display > Screen timeout > Never (or use Fully Kiosk's "Keep Screen On")
- **iPad**: Settings > Display & Brightness > Auto-Lock > Never
- **Linux**: `xset s off && xset -dpms`
